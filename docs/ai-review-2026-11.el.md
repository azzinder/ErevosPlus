# Έλεγχος ασφαλείας με τη βοήθεια AI, Νοέμβριος 2026

[English](ai-review-2026-11.md)

**Τι ήταν.** Έλεγχος ασφαλείας του κώδικα του Erevos με τη βοήθεια ενός μοντέλου AI (ChatGPT), με
τις διαδικασίες του VIDOC Security Review (έλεγχος κώδικα, επαλήθευση ευρημάτων, αναφορές), το
Security Advisory Scout (OSV, NVD, FIRST EPSS, CISA KEV) και το Authorized Security Review. Είναι
διαδικασίες που τρέχουν στον κώδικα που τους δίνεται· αυτή της VIDOC δεν συνδέεται με την πλατφόρμα
ή την υπηρεσία σάρωσης της Vidoc.
**Τι δεν ήταν.** Audit, πιστοποίηση, ή έλεγχος από άνθρωπο εκτός του έργου.

**Τι ελέγχθηκε.** Το main του azzinder/Erevos `6afe952e` (22 Νοεμβρίου 2026), μετά το Erevos
3.0.0-beta.2 (`b49c6bb9`, 22 Νοεμβρίου) και η γραμμή του 3.0.0-rc.1 (`f27c8d94`). Κυρίως ανάγνωση
του κώδικα, και μερικά tests που έγραψε ο έλεγχος· τα tests του Rust και της εφαρμογής τα τρέξαμε
εμείς.

**Πώς χειριστήκαμε τα ευρήματα.** Κάθε ένα ελέγχθηκε πρώτα στον κώδικα. Τρία δεν στέκουν όπως
γράφτηκαν: η έλλειψη ελέγχου υπογραφής JWT (επιτρέπεται από το OpenID Connect Core 3.1.3.7 για
token από το token endpoint μέσω TLS), το όριο μεγέθους για chunked HTTP (το όριο μετρά τα bytes που
φτάνουν, το πολύ περίπου 260 KiB), και η «μη καρφωμένη» έκδοση του Rust (την καρφώνει το
`rust-toolchain.toml`).

Περιορίστηκε: **LOCK-02** (ένα PIN 4 ψηφίων μπορεί να βρεθεί offline από όποιον έχει ένα backup
και τον κωδικό του). Το ελάχιστο μένει 4 χαρακτήρες, αλλά ένας αδύναμος κωδικός ή PIN θέλει τώρα
δεύτερη επιβεβαίωση, και ο οδηγός λέει γιατί.

Προστέθηκε μετά τον έλεγχο: test ότι ένα relay ρωτά ένα όνομα μία φορά και συνδέεται μόνο σε
διευθύνσεις που πέρασαν το φίλτρο του (DNS rebinding), στο main μετά το 3.0.0-rc.1.

## Δεν καλύφθηκαν

- Μέτρηση χρόνου των ελέγχων PIN σε πραγματικό κινητό.
- DNS rebinding με πραγματικό resolver σε εργαστήριο (η συμπεριφορά του relay ελέγχεται με ψεύτικο).
- Δοκιμές με πραγματική διακοπή ρεύματος.
- Fuzzing, και έλεγχος από άνθρωπο με εμπειρία στην κρυπτογραφία.
